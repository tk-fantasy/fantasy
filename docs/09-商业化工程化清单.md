## 1. 远程运维通道（P0）

局域网盒子的最大痛点：出了问题，你在办公室，设备在客户机柜里。

**需求**
- 无需客户开放公网端口，即可远程查看日志 / 执行诊断命令 / 重启服务
- 必须双向鉴权，通道本身不能成为客户网络的入侵入口

**方案**
- 反向隧道方案：内网侧跑 `frp` 或自建 `wstunnel` 客户端连到你的运维网关（一台云服务器），公网侧通过一次性的短时令牌连接
- 兜底方案（低成本先行）：内置"诊断包导出"功能 —— 一键打包 `logs/` + `config.json`（脱敏）+ 系统信息（`uname`、`docker ps`、磁盘/内存），生成 zip 发给客户传回，先满足 80% 的排障场景
- 所有远程操作写审计日志：谁、何时、执行了什么（中厂验收的底线）

**验收标准**
- [x] 客户侧一条命令或界面按钮即导出脱敏诊断包（2026-08-15）
- [ ] ~~隧道通道：客户无需开放防火墙端口，云端可下发只读指令~~ → **方案调整（2026-08-15）**：不做反向隧道。当前部署形态为自有树莓派、开发者远程操控，无第三方客户机柜场景；隧道等出现真实远程交付客户时再评估
- [x] 全部远程操作有审计记录（2026-08-15，范围：诊断包导出；后续新增运维操作须接入 `app/ops/audit.py`）
- [ ] ~~通道可随时由客户侧一键切断~~ → 随隧道方案一并搁置（无通道即无需切断）

**涉及改动**：`app/` 新增 `ops/` 模块（diag、audit）、`scripts/` 新增诊断打包脚本

> **实施记录（2026-08-15）**：`app/ops/diag.py`（脱敏打包：密钥字段打码 + home 段/设备 MAC 占位，URL/设备名/IP/日志保留；日志每文件取尾部 2MB、总量 10MB；docker ps 经 docker.sock UDS）+ `app/ops/audit.py`（JSONL 审计 `logs/audit/ops_audit.jsonl`）+ `GET /api/ops/diagnostics`（登录后下载）+ `GET /api/ops/audit` + 高级设置「运维 → 导出诊断包」按钮 + `scripts/export_diag.py` 命令行版（API 与 CLI 共用同一脱敏逻辑）。14 个单测。

## 2. 离线升级链路（P1）

不能依赖客户网络拉 Docker Hub，升级失败必须可回滚。

**需求**
- 生成离线升级包（镜像 tar + 版本 manifest + 升级脚本）
- 支持版本检查、备份回滚、升级失败自动恢复

**方案**
- 版本号规范：`AETHER_APP` 常量 + `version.json`（语义化版本 + 兼容的最低配置版本）
- 升级包结构：
  ```
  aether-update-1.3.0.tar.gz
  ├── manifest.json        # 版本号、依赖镜像、哈希校验、变更说明
  ├── images/              # docker save 出的镜像
  └── scripts/upgrade.sh   # 停服 → 备份 → 换镜像 → 迁移 → 启服 → 自检
  ```
- 升级脚本关键步骤：升级前备份 `config.json`、数据库、HA 配置目录；迁移靠 Alembic（项目已有）；失败自动回滚到上一版镜像并恢复备份

**验收标准**
- [ ] 一条命令 `./upgrade.sh aether-update-1.3.0.tar.gz` 完成升级
- [ ] 断网环境（彻底无外网）可完成安装和升级
- [ ] 故意制造失败步骤（如破坏镜像），能自动回滚且数据不丢
- [ ] 版本不兼容（配置/数据库过旧）时友好报错并中止

**涉及改动**：`docker-compose.yml` 版本固定、`scripts/` 新增 `build-update-pack.py` + `upgrade.sh`、`version.json`

## 3. 部署体检与网络自检（P1）

客户现场网络千奇百怪（双网卡、VLAN、上游防火墙、NAS 抢端口）。

**需求**
- 部署时一键体检：端口占用、网络连通性、磁盘空间、内存、时间同步、摄像头 RTSP 可达性
- 出问题直接给出"修复建议"，而不是让客户贴日志

**方案**
- `scripts/diagnose.py`，输出结构化 JSON + 人类可读报告，检查项：
  - 端口检查：`8000`（后端）、HA 端口、MQTT（mosquitto）端口是否被占用
  - 网络检查：HA 地址可达、摄像头 RTSP 可达（`cv2.VideoCapture` 3 秒超时）、DNS 是否正常（云端模型模式需要）
  - 资源检查：磁盘剩余 > 2GB、内存 > 2GB、CPU 架构（x86/arm 检测，项目已有 check_arm_backend.py）
  - 时间检查：NTP 同步状态（摄像头 RTSP 对时间敏感）
- 生成离线 HTML 报告，客户截图/上传即可支持排障

**验收标准**
- [ ] 一键运行，平均 < 30 秒出报告
- [ ] 每项检查有"通过/警告/失败 + 怎么办"三段式提示
- [ ] RTSP 不可达时能区分"网络不通 / 凭据错误 / 格式不支持"

**涉及改动**：`scripts/`（尊重现有 `check_arm_backend.py`、`diag_camera.py` 的成果，扩展为全量体检）

## 4. 模型出网策略与双模式声明（P0）

摄像头画面与设备控制不出网 ✅，但对话文本走云端 API 时会出网 —— 必须让客户知情，或提供"全内网版本"卖溢价。

**需求**
- 明确两种运行模式，配置化切换，随产品文档/合同写明
- 云端模式：对话走加密 HTTPS 到模型服务商（现状），画面/设备不出网
- 纯内网模式：本地跑 Ollama/vLLM 小模型，一切不出网

**方案**
- `config.json` 增加 `egress_policy`：`cloud` | `local` | `hybrid`（hybrid = 默认云端对话、敏感功能强制本地）
- 首次启动引导页让用户选择模式并展示对应声明文案（留存签署确认）
- 纯内网模式：脚本一键装 Ollama + 拉取预设模型（如 Qwen 系列小模型）；对话模型/视觉模型指向本地端点
- 提供一页 PDF/网页版《数据流向说明》给集成商用作销售材料

**验收标准**
- [x] 三档模式可无代码切换，聊天页标出当前模式徽标（2026-08-15）
- [ ] 纯内网模式断网状态下全部功能可用（待现场部署验证：内网模型机器发布 OpenAI 兼容端点后实测）
- [x] 引导页声明已确认后不可误触跳过（记录 hash 到存储）（2026-08-15）
- [ ] 销售材料页可导出（《数据流向说明》已产出 `docs/tech/数据流向说明.md`，可浏览器打印转 PDF；一键导出后置）

**涉及改动**：`app/core/config.py`、`app/services`（模型路由加本地端点）、`frontend`（模式徽标 + 引导页）、`docs/` 新增《数据流向说明》

> **实施记录（2026-08-15）**：`app/services/egress_service.py` + `app/routes/egress_routes.py`（GET/POST `/api/egress` + `/api/egress/confirm`，确认记录含确认人/时间/模式/文案版本 SHA-256，存 DB kv `egress_confirm`）；引导页第 4 步（老用户升级直达补签）；聊天页徽标（`useEgressMode` composable）；高级设置「数据出网模式」卡片+弹窗。
> 决策：①执行力度为**声明级**（local 模式有公网端点只警告不拦截，避免锁死）；②纯内网模型跑在内网任意机器（如 Mac 上的 Ollama/LM Studio/vLLM），以 OpenAI 兼容端点经「API Keys」接入，不做一键安装脚本（模型在客户内网机器上，非树莓派本体）；③`/api/setup/status` 新增 `egress_confirmed` 字段。

## 实施顺序建议（串行版）

```
第 1 步：条目 4（模型出网声明）→ 影响合同，最便宜，先做
第 2 步：条目 1（诊断包导出）→ 没有它，后面每单排障都烧钱
第 3 步：条目 3（体检脚本）→ 部署成功率直接决定口碑
第 4 步：条目 2（离线升级）→ 有第一个客户后再做也来得及，但升级脚本框架先搭好
第 5 步：条目 6（备份恢复）→ 随便什么客户提一句就得有
第 6 步：条目 7（商务物料）→ 有销售在跟单时，同步准备
（backlog：云端监控面板 + 告警，等交付 3~5 台设备后再考虑）
```

> 原则：**先做人肉可用的（诊断包、体检脚本），再做自动化（隧道、心跳）**。
> 每个条目完成前不要开下一个 —— 这些是"交付信誉"的保险，不是功能堆砌。
